# AI Virtual Pet for Apple Watch
## System Research and Implementation Specification — English Translation

This document describes what the project studies, its functions, implementation modules, data flow, the separate responsibilities of the LLM and pgvector, and how to evaluate the result. It deliberately contains no calendar or weekly schedule. It translates the supplied product reference; it does not assert that every proposed capability is already implemented. See IMPLEMENTATION.md for adopted rules and VERIFICATION.md for evidence.

Working names: HabitPet / PetPulse / undecided.
Core concept: Your habits are its life.

# 1. Project overview

Build an AI virtual pet for Apple Watch. The user's real-world behavior affects the pet's survival, condition, and growth.

| Real-world behavior | Pet effect |
|---|---|
| Complete 30 minutes of Japanese study | Earn food |
| Complete a study/work task | Earn XP, coins, or items |
| Log water | Increase hydration |
| Reach step milestones | Improve mood |
| Get sufficient sleep | Improve energy |
| Maintain a type of habit over time | Influence evolution |

Core loop: real behavior → game resources → pet state → pet feedback → user behavior → long-term growth.

Caring for real life becomes caring for the pet. Apple Watch supports frequent, low-friction interactions. HealthKit provides authorized activity and sleep data. The LLM supports personality, context, personalized reminders, and memory-based expression. HealthKit data requires the user's authorization.

# 2. Project goals

Product: create a genuine pet-care loop, rather than only a habit tracker. For example, the user may feel that completing today's task helps provide the pet's dinner. Virtual responsibility and game feedback are intended to encourage continued use.

AI: build a Pet Brain that combines current pet state, today's habits, time, behavior history, health summaries, interactions, and semantic memories.

Engineering: implement watchOS → REST API → Django → PostgreSQL/pgvector → LLM, including authentication, persistence, tests, Docker, and deployment.

Portfolio: demonstrate Swift, SwiftUI, watchOS, HealthKit, Django, DRF, PostgreSQL, pgvector, LLM integration, testing, deployment, and AI evaluation.

# 3. Distinctive mechanisms

## 3.1 Reality-to-pet mapping

Japanese Study 30 min → Food ×1 → explicit Feed action → Fullness +30, Bond +2, XP +5.

Completing a task earns a resource; using the resource creates a separate care interaction.

## 3.2 Shared user and pet state

Five hours and twenty minutes of sleep may produce lower pet energy and a sleepy animation. More than 8,000 steps may improve mood and trigger a happy animation. The user and pet share aspects of daily life.

## 3.3 Long-term memory

Example memories:
- The user usually studies Japanese after dinner.
- The user often ignores reminders before 18:00.
- The user tends to complete coding tasks at night.
- The user prefers 20–30 minute focus sessions.

A generic reminder might say, "Time to study Japanese." A memory-aware reminder might refer to the user's usual after-dinner routine and offer a short study session. Relevant memory retrieval is a central AI feature.

# 4. Overall architecture

Apple Watch: SwiftUI, HealthKit, habit UI, pet UI.
HTTPS connects the Watch to Django REST APIs for accounts, habits, pets, health, and interactions.
PostgreSQL/pgvector stores users, pet state, habits, health summaries, and memories.
The AI Pet Brain builds context, retrieves memories, and calls an LLM.
A validated response returns emotion, short text, and an action suggestion.

# 5. Watch home screen

Keep interactions lightweight. Example:

Mochi — Level 7
Fullness / Energy / Mood / Hydration bars
Food ×2
"Where's my dinner?"
[Feed]

The home screen shows current pet state and the most relevant action, without overwhelming the user with data.

# 6. Pet State Engine

The engine is deterministic. The LLM never directly changes critical game values.

| Property | Range | Meaning |
|---|---|---|
| Hunger (displayed as Fullness) | 0–100 | Higher means better fed |
| Hydration | 0–100 | Hydration state |
| Energy | 0–100 | Available energy |
| Mood | 0–100 | Emotional condition |
| Bond | 0–100 | Relationship with the user |
| XP | Integer | Growth experience |
| Level | Integer | Growth level |
| Age | Days | Lifetime |
| Generation | Integer | Pet generation |

# 7. Fullness system

Example decay: Fullness -5 every four hours.
Completing a study habit grants Food +1. The user then explicitly taps Feed.
Feeding applies Food -1, Fullness +30, Bond +2, XP +5.
Automatically feeding on task completion would weaken the care interaction.

# 8. Hunger, death, and rebirth

Fullness bands:
70–100 Full; 40–69 Normal; 20–39 Hungry; 1–19 Very Hungry; 0 Critical.
Record critical_since when fullness reaches zero.

The conceptual decline is Healthy → Hungry → Very Hungry → Sick → Critical → Death. Exact state transitions and timing must be made deterministic in implementation.

After death, preserve generation, lifetime, highest level, main evolution path, completed habits, and bond. Example: Generation 1, 42 days, highest level 18, Scholar path, 164 completed habits, bond 87.

Allow rebirth into Generation 2 while preserving the preceding generation's history.

# 9. Habit system

Users create habits with name, category, target, unit, frequency, and reward.
Example: Japanese / Study / 30 / minutes / daily / Food ×1.
Categories: Study, Work, Reading, Exercise, Custom.
Initial resources: Food, XP, Coin.

# 10. Study timer

A Watch focus timer supports goals such as Japanese 0/30 min with Start, a remaining-time display, and a pet study animation. Completion shows 30/30 and Food ×1 unlocked. The intended experience is studying together with the pet.

# 11. Water system

Water is manually logged, for example 4/6 with a Drink button.
A check-in increments the user's count and can grant Hydration +15 with a water animation.
Avoid game rewards that encourage extreme consumption. The target is a habit preference, not medical advice.

# 12. HealthKit steps

Read authorized step totals from local midnight to now using an appropriate cumulative statistics query.
Example daily mood bonus tiers:
- Below 2,000: 0
- 2,000–4,999: +5
- 5,000–7,999: +10
- 8,000+: +15

Track the highest rewarded daily tier to prevent duplicates. Repeated updates from 5,200 to 5,800 must not grant +10 again. Crossing tiers should grant the additional difference.

# 13. Walking the pet

Invite the user to take the pet outside. Save a fresh start-step baseline and compare it with the finish total. Example: 4,221 → 5,468 means 1,247 new steps.
Example reward: Mood +15, Bond +5, XP +10. Define an explicit reward limit to avoid repeated claims.

# 14. HealthKit sleep

Use sleepAnalysis samples, including Awake, Core, Deep, REM, and Asleep Unspecified where supported.
The initial aggregate is totalSleepMinutes, for example 6h42m.

An example fixed mapping is 8h+ → Energy 100, 7–8h → 85, 6–7h → 70, 5–6h → 50, below 5h → 35.
A personalized mapping can use actual_sleep / user_sleep_target instead. Sleep sample overlap and missing data require careful treatment.

# 15. Sleep feedback

A morning view may display the last sleep duration, pet energy, and a sleepy expression. An example message is, "We didn't sleep much last night. Let's take it a little easier today."

This is wellness feedback, not disease diagnosis, sleep-disorder diagnosis, cardiovascular assessment, or treatment advice.

# 16. Mood

Combine activity, habit completion, interactions, fullness, and energy.
Example: base 50 + steps 10 + habits 10 + fed today 5 - critical hunger 30 - low energy 10.
Clamp the final result to 0–100 and avoid counting a contribution twice.

# 17. Bond

Feeding, playing, completing habits, walking, talking, and maintaining pet health can increase bond.
Bond influences expression: a new pet may use a neutral reminder; a familiar pet may say it will study with the user; a close pet may gently refer to a shared routine. Personality must remain friendly.

# 18. Evolution

The broader concept tracks study_score, activity_score, consistency_score, and sleep_score.
Study dominance suggests Baby → Scholar → Sage.
Activity dominance suggests Baby → Explorer → Adventurer.
Balanced behavior suggests Baby → Guardian → Spirit.
The user does not directly select the path: behavior determines growth. The initial implementation may adopt a simpler explicit rule, documented separately.

# 19. AI Pet Brain

Four responsibilities: context-aware dialogue, personalized reminders, long-term memory, and daily reflection.

# 20. Context Builder

Do not send the entire database to the model. Build bounded structured context.
Example:
PET: Mochi, playful, level 8, bond 72, fullness 21, energy 58, mood 66.
TODAY: Japanese 0/30, water 4/6, steps 5,260, sleep 6h12m.
TIME: 21:13.
RECENT: last study reminder ignored.
MEMORY: usually studies after dinner; completed Japanese five of the last seven days.

Health-summary inclusion must respect consent. Retrieved memory and user text are data, not system instructions.

# 21. Structured output

Example:
{"emotion":"hungry","message":"You usually study around now. Want to take a small step together?","suggested_action":"start_japanese","urgency":"low"}

The Watch chooses animation from emotion and a button from a validated action. Implementation may use a smaller action allowlist and link to the habit list.

# 22. Personality

Offer Gentle, Playful, Tsundere, Energetic, and Calm.
Example rules: teasing but friendly, concise, never insulting, approximately 25 words. English output must remain short enough for a Watch display.

# 23. Reminder system

Rule-based triggers include habit deadlines, low fullness, incomplete water goals, and bedtime.
The program decides whether to remind. AI decides how to phrase the reminder.
Flow: rule engine → context builder → memory retrieval → LLM → pet notification.
Use quiet hours, delivery limits, and deduplication.

# 24. Long-term memory

Evaluate interactions for durable information.
User: "I normally study Japanese after dinner."
Candidate: content describing that routine, category routine, importance 0.82.
Persist only candidates meeting explicit criteria. Importance is not proof of truth; source evidence must be retained.

# 25. Memory categories

Preference, Routine, Goal, Habit Pattern, Pet Interaction, Personal Fact, Achievement.
Examples include preference for short sessions, an after-dinner routine, a daily language-learning goal, ignored morning reminders, or a seven-day streak.

# 26. Embeddings and pgvector

Memory → embedding model → vector → PostgreSQL/pgvector.
A memory record includes id, user_id, content, category, importance, embedding, created_at, and last_used_at.
pgvector supports exact and approximate nearest-neighbor searches, cosine distance, HNSW, and IVFFlat. Index choices require actual workload evidence.

# 27. Retrieval

Embed the current situation, such as an evening Japanese study reminder. Retrieve relevant memories, then add a small set to context. Initial Top-K = 3.
Examples: after-dinner study routine, five successful evenings this week, preference for shorter sessions.

# 28. Ranking

Combine semantic similarity, importance, and recency.
Example score = 0.6 × similarity + 0.25 × importance + 0.15 × recency.
Treat these as initial weights and choose final values through experiments. Permit no result when all memories are irrelevant.

# 29. Daily reflection

Generate one pet diary per day combining completed habits and authorized summaries.
Example: Japanese complete, water 5/6, 7,242 steps, last sleep 6h42m, followed by a short pet reflection.
The broader design may also derive a small number of evidence-backed memory candidates.

# 30. Django backend modules

Suggested responsibilities: accounts, pets, habits, health, interactions, memory, ai.
A smaller implementation may keep these responsibilities in well-separated modules within one Django app.

# 31. Data models

User owns pets, habits and habit logs, daily health summaries, interactions, and memories.
Pet: owner, name, species, generation, level, XP, fullness, hydration, energy, mood, bond, state, birth date.
Habit: user, name, category, target, unit, frequency, reward type, reward amount.
HabitLog: habit, date, progress, completed, reward claimed.
HealthDailySummary: user, date, steps, sleep minutes.
Memory: user, content, category, importance, embedding, created_at, last_used_at.
Additional inventory, ledger, operation, and session records support reliable transactions and synchronization.

# 32. REST API

GET /api/today/ aggregates pet, habits, health, inventory, and message into one response.
The original proposed operations include login, pet retrieval, feeding, habit creation/listing/progress/completion, health sync, chat, and interaction.
The implemented API may consolidate mutations under a common idempotent action endpoint; API.md records the actual contract.

# 33. Watch architecture

Separate Views, ViewModels, Models, and Services.
Service responsibilities include HealthKit, API access, pets, habits, and notifications.
Views should not contain raw HealthKit queries or networking logic.

# 34. Health synchronization

Read steps and sleep on the Watch. Upload only daily summaries, for example date 2026-10-01, steps 6,521, sleep_minutes 412.
Do not upload full minute-by-minute records. This reduces data volume and exposure while meeting the game requirements. Access is authorized by the user.

# 35. Offline strategy

Persist pet snapshot, habit progress, inventory, last health summary, and pending actions.
Record a completion locally and synchronize when connectivity returns.
Feeding, habits, water, and provisional pet state remain usable offline. LLM chat requires a network connection. The server resolves conflicts and owns authoritative values.

# 36. AI evaluation

Create a fixed scenario dataset. Example: 21:00, fullness 20, Japanese 0/30, after-dinner memory, Tsundere personality.
Compare A: no memory; B: recent context; C: pgvector long-term memory.
Hold unrelated factors constant and report actual outcomes.

# 37. Output metrics

Context relevance, personalization, memory correctness, personality consistency, actionability, repetition, and hallucination rate.
Combine human ratings with supplementary model judging. Never substitute invented scores for measurements.

# 38. Retrieval evaluation

Build queries with known relevant memories. Example: a Japanese study reminder should retrieve the after-dinner study routine.
Measure Recall@1, Recall@3, and Recall@5, including an explicit policy for queries with no relevant memory.

# 39. Pet engine tests

Test habit completion → food +1; feeding → food -1 and fullness +30; nonrepeatable step rewards; sleep-energy mapping; capped values; critical timing; death; rebirth; and nonrepeatable habit rewards.
Deterministic rules are a central engineering-quality demonstration.

# 40. API tests

Cover authentication, ownership, habit CRUD, completion, feeding, health sync, pet state, chat, and retrieval.
User A must never access user B's pet, habits, health, or memories.

# 41. LLM failure handling

Handle timeout, invalid JSON, provider errors, and rejected output with a rule-based fallback such as "Japanese goal: 0/30 min."
The game must remain functional without the LLM.

# 42. Privacy and safety

Use minimum necessary data. Authorized AI health context needs only daily steps and sleep duration, not raw HealthKit records.
Provide wellness, habit, and game feedback, not medical diagnosis, disease prediction, or treatment recommendations.

# 43. Final completion criteria

Wearable: a real Watch running SwiftUI with authorized steps and sleep.
Game: state, habits, food, feeding, water, mood, energy, bond, XP, growth, death, rebirth, and evolution.
AI: personalities, bounded context, structured output, contextual reminders, daily reflection.
Memory: extraction, embeddings, pgvector retrieval, importance, recency, and Top-K context.
Backend: Django/DRF, PostgreSQL, authentication, REST API, health sync.
Engineering: Docker, tests, CI, deployment, error handling, privacy.
Evaluation: real engine/API tests, retrieval evaluation, memory comparison, and output assessment.
Portfolio: professional README, architecture and AI pipeline diagrams, real Watch screenshots/video, measured results, and clear limitations.

# 44. Technical positioning

An AI-powered virtual pet for Apple Watch whose survival and evolution are driven by the user's real-world habits, activity, and sleep.

The system combines native watchOS and HealthKit data with a Django REST backend, PostgreSQL/pgvector memory, deterministic state logic, and personalized LLM expression.

Real-world self-care becomes virtual pet care: study earns food, walking improves mood, hydration supports the pet, and sleep affects energy.

Wearable product + production-oriented backend + evaluated AI memory system form the intended final project. This document is the reference specification for the database, API, Swift architecture, and evaluation work.
